## 2. 🔐 Sécurité

### 🔴 CRITIQUE

**S1 — Endpoint `/api/contacts` accessible sans authentification**
- Fichier : `backend/server.py` (≈ ligne 204)
- `GET /api/contacts` renvoie **toutes** les demandes de contact (nom, email, téléphone, message) sans aucun contrôle d'accès.
- **Impact** : fuite de données personnelles (RGPD), n'importe qui peut lire la liste complète des prospects.
- **Reco** : protéger par `Depends(require_admin)` comme les autres routes admin.

### 🟠 IMPORTANT

**S2 — CORS trop permissif**
- Fichier : `backend/server.py` (≈ ligne 273) + `.env` `CORS_ORIGINS="*"`
- `allow_origins=["*"]` combiné à `allow_credentials=True` : configuration non conforme à la spec CORS et trop ouverte pour de la production.
- **Reco** : renseigner explicitement `CORS_ORIGINS="https://syndicatducode.fr,https://lacitadellenumerique.fr"` dans `.env`.

**S3 — Webhook Stripe sans vérification de signature effective**
- Fichier : `backend/routes/citadelle/payments.py` (≈ ligne 212)
- Le handler avale toutes les exceptions et renvoie toujours `{"received": True}`. La signature `Stripe-Signature` n'est pas réellement validée et aucun traitement métier n'est déclenché par le webhook.
- **Impact** : sécurité (faux événements possibles) **et** fiabilité (cf. F1).
- **Reco** : valider la signature avec le secret webhook (`STRIPE_WEBHOOK_SECRET` à ajouter en `.env`) et traiter l'événement `checkout.session.completed`.

### 🟡 MOYEN

**S4 — Secret JWT avec valeur de repli en dur** (violation Règle 5)
- Fichier : `backend/config/settings.py` (ligne 19) — fallback `'syndicat-du-code-secret-key-change-in-production'`.
- En prod le `.env` surcharge bien, mais le fallback dangereux subsiste. **Reco** : supprimer la valeur par défaut → échec explicite si la variable manque.

**S5 — Brute-force calculé sur la mauvaise IP au login Citadelle**
- Fichier : `backend/routes/citadelle/auth.py` (ligne 298) — utilise `request.client.host` (= IP du proxy K8s) alors que l'inscription, elle, lit correctement `X-Forwarded-For`.
- **Impact** : derrière le proxy, soit tous les utilisateurs partagent la même IP (blocage collectif), soit la protection est inefficace.
- **Reco** : centraliser une fonction `get_client_ip(request)` (DRY) et l'utiliser partout.

**S6 — Upload du formulaire `/api/contact` sans validation**
- Fichier : `backend/server.py` (≈ ligne 152) — aucun contrôle de type MIME ni de taille (contrairement à l'upload des annonces Citadelle qui, lui, est bien sécurisé : types autorisés + 5 Mo max).
- **Reco** : appliquer la même liste blanche + limite de taille.

**S7 — Dépendance `python-jose`**
- CVE connues (confusion d'algorithme). L'usage en HS256 fixe atténue le risque, mais une migration vers `PyJWT` est recommandée à terme.

### 🟢 Points positifs sécurité
- Mots de passe hashés en **bcrypt** (`passlib`).
- Tokens de réinitialisation stockés **hashés** (SHA-256), à usage unique, expiration 1 h.
- `forgot-password` ne révèle pas l'existence d'un compte (anti-énumération).
- Isolation stricte des plateformes (`platform: citadelle` vs `syndicat`).
- Routes admin Citadelle correctement protégées (`Depends(require_admin)`).
- `.env` bien ignoré par git ; clé Stripe publishable (`pk_live`) côté front = normal.
- Masquage automatique des coordonnées dans la messagerie (`message_sanitizer.py`).

## 3. 🧱 Qualité du code

### 🟢 Forces
- **Architecture modulaire claire** (Règle 16) : `routes/` par domaine, `services/`, `middleware/`, `config/`, `models/`, `utils/`.
- **Zéro hardcoding d'URL côté frontend** : tout passe par `REACT_APP_BACKEND_URL`.
- **Constantes centralisées** (`citadelleConstants.js`, `config/settings.py`) — DRY globalement respecté.
- `datetime.now(timezone.utc)` utilisé partout (pas de `utcnow()` déprécié).
- Index MongoDB bien définis au démarrage.

### 🟠 Points d'amélioration
**Q1 — Fichiers trop volumineux (Règle 17 : viser < 700 lignes)**
| Fichier | Lignes |
|---------|--------|
| `backend/services/email_service.py` | 1 860 |
| `backend/routes/citadelle/transactions.py` | 1 225 |
| `backend/routes/citadelle/auth.py` | 844 |
| `frontend/.../CitadelleTransactionDetail.js` | 871 |
| `frontend/.../CitadelleVendre.js` | 782 |
| `backend/routes/citadelle/listings.py` | 703 |

**Q2 — Duplication (violation DRY ponctuelle)**
- Helpers de token de reset dupliqués : `services/auth_service.py` **et** `routes/citadelle/auth.py` (`_generate_reset_token`, `_verify_reset_token`). La version Citadelle utilise `==` au lieu de `secrets.compare_digest` (moins sûr, timing attack théorique).
- Vérification du rôle admin réimplémentée plusieurs fois (`middleware/auth.py`, `services.py`, `auth.py:_require_admin`, etc.).
- Extraction manuelle du token Bearer répétée (`/me`, `/accept-cgu`, `/profile`) au lieu d'utiliser `Depends(get_current_user)`.

**Reco** : mutualiser via le middleware existant et `auth_service`. ⚠️ Refactoring à valider avant exécution (Règles 8, 9, 12).

## 4. ⚙️ Fiabilité

**F1 — Confirmation de paiement fragile (polling uniquement)**
- Fichier : `payments.py` — la validation repose sur l'appel client `GET /payments/service/status/{session_id}`. Si l'acheteur ferme l'onglet après paiement, la transaction reste `pending` et **aucun email n'est envoyé**.
- **Reco** : fiabiliser via le webhook Stripe (cf. S3) comme source de vérité.

**F2 — `decode_access_token` renvoie `None` → 500 au lieu de 401**
- Fichier : `routes/citadelle/auth.py` (`/me` ligne 363, `/accept-cgu` ligne 809). Le `try/except` ne capture rien car la fonction ne lève pas d'exception ; `decoded.get(...)` plante ensuite → erreur 500 (violation Règle 19).
- **Reco** : tester `if decoded is None: 401`.

**F3 — `/contacts` charge 100 documents en dur** ; `reset-password` itère sur 100 tokens — acceptable à faible volume, à indexer/optimiser si la base grossit.

### 🟢 Points positifs fiabilité
- Gestion d'erreurs présente sur les appels Stripe/SMTP (logs + `HTTPException`).
- Idempotence du seeding des services.
- Anti-doublon des emails vendeur (`seller_notified_at`, `reminder_sent_at`).
